# CA01 factory GUI — Ghidra reverse-engineering findings

**Analysis date:** 2026-10-22/23 (EDT)
**Scope:** Static analysis only. No recovered Toyota program was executed, no car was connected, and no firmware was installed, decrypted, signed or flashed. Analysis artifacts stay **outside the Git checkout**.

## Binary provenance

- HMI: `system-audit/ca01-updater-independent-20261022/06-PROC_HMI`, SHA-256 `cf7c621b96d0865d7ba5d79a6aa8806e3d2544a827966a27a7c95de56ffa6503`.
- System library: `system-audit/ca01-updater-independent-20261022/06-libipas_sysc.so`, SHA-256 `a1f2812d0b1776fa79dcb9ebddd5dca2d16443f77db19c35f4aac2cbabc302b4`.
- Ghidra 12.1.4, Java 21, ELF ARM32 little-endian imports (not a raw-file guessed base).
- Ghidra recognized 8,877 functions in HMI. Many symbols are automatically synthesized or PLT/import labels. Function names below beginning `FUN_` are Ghidra-assigned, not official vendor names.
- The independent static dynamic-symbol audit found 55 directly imported GLES1-style functions and 18 EGL functions. Mesa ARMEL libraries export all 55 and 18 corresponding symbol **names**, respectively. This is **not** proof of ABI, initialization, graphics or OS compatibility.
- HMI still declares `libOpenVG.so` in ELF DT_NEEDED, but no direct `vg*` imports were seen in the dynamic symbol table; no conclusion is made about library constructors, indirect use, or safe omission.

## Reconstructed HMI startup

1. ELF entry `0x0000d8f8` uses `__libc_start_main` with application main `0x00123eb8`.
2. Decompilation of main `FUN_00123eb8` shows option `-v`, prints `[HMI]` and embedded build date `Nov 10 2017 17:05:22`, calls `fs_sys_CnfEntry(&PTR_DAT_0059f948)`, then `SysPowerOn(9)`.
3. Both `fs_sys_CnfEntry` (ELF exported offset `0x0001dde0`) and `SysPowerOn` (ELF exported offset `0x0000aeac`) exist in recovered `libipas_sysc.so`. **Ghidra in that shared object uses rebased internal addresses (`0x0002dde0`, `0x0001aeac`)**. Always retain original ELF symbol offsets when correlating disassembly.
4. Decompiled `SysPowerOn` loads configuration (`fs_cnf_Load`), initializes process, system, task, IPC, shared-memory and PSM services (`fs_prc_Init`, `fs_sys_InitCom`, `fs_tsk_Init`, `fs_ipc_Init`, `fs_shm_Init`, `fs_psm_Init`). It traverses configured IPC/PSM/shared-memory entries, calls `fs_sys_ExInit` and eventually dispatches indirectly to `fc_sys_AccStart(param_1)`. These are *dependent services*; dummy no-op libraries would hide actual startup requirements.

## Actual GUI graphics path (Ghidra-confirmed call sites)

- `FUN_0002bb08`: calls `sysDisMngInit` (via `FUN_00016094`), constructs a native window (`FUN_0002b66c`), then `eglGetDisplay(0)`, `eglInitialize`, `eglChooseConfig`, `eglCreateContext`, `eglCreateWindowSurface`, `eglMakeCurrent`. Called by `FUN_001ce540`.
- Configuration array at `0x00296324` requests 32-bit buffer, 16-bit depth, `EGL_WINDOW_BIT` surface, zero sample buffers and 8-bit red/green/blue/alpha. The exact decompiler calling prototypes are incomplete; use EGL specification when building tests.
- `FUN_0002b66c` builds a 32-byte native-window object with width/height obtained indirectly from vehicle/config parameters via `rq_sys_GetVclPara` in `FUN_0002a548`. It references display buffer addresses and a plane count.
- **Triple buffering:** `FUN_00016054` calls `sysDisMngMemAlloc(width * height * 4, ...)` three times. `FUN_00015f7c` returns the constant `3`. `FUN_00015f18` accesses up to three display-buffer handles. This is a concrete framebuffer contract for an eventual software display adapter, not proof of guest runtime graphics.
- `FUN_0002b9fc`: calls `eglSwapBuffers` then a callback and the display-planar update sequence (`FUN_00015fb8`, `FUN_00015f84`). Called from `FUN_001ce0a4`. `FUN_00015f84` invokes `sysDisMngPlnDispSw`, `sysDisMngPlnAlpha` and `sysDisMngPlnTrans`. Some frame updates also call `eglSwapBuffers` from `FUN_00015c00`.
- `FUN_0002b944` explicitly creates an EGL **pbuffer** through `eglCreatePbufferSurface`. Partial off-screen work may be practical if the remaining runtime dependencies can be satisfied. This does not convert the primary native-window path to pbuffer automatically.
- `FUN_001de9c0` uses fixed-pipeline GL state and drawing calls; `FUN_001e06d8` uses `glDrawArrays` and `glDrawElements`, establishing that real rendered geometry is generated by HMI code.
- `FUN_0002bae8` requests `glBlendFuncSeparateOES` via `eglGetProcAddress`, so an adapter must preserve extensions and indirect function lookup when relevant.

## IPC and interface state

- `FUN_0002b22c` performs a repeated message loop involving `rq_msg_ReceiveT(0x28, ...)` and `rq_msg_ReceiveP(0x28, ...)`, timer and task calls.
- `FUN_0002b170` dispatches a `0x41002` message to `FUN_0002b054` and handles `0` specially; other codes trigger diagnostics. Argument/types of the queue service are unverified.
- Because the program creates IPC/task/shm resources and receives messages before drawing normal screens, recovering the graphics symbols alone is insufficient to run the real UI.

## Original language resources recovered

Six validated GUI TAR entries represent **three unique XML paths**, each recovered twice with identical SHA-256:
- `./opt/ftl/gui/allwords/13UP_EN-US-NA_DA-Base_FormatA.xml`
- `./opt/ftl/gui/allwords/13UP_FR-CA_DA-Base_FormatA.xml`
- `./opt/ftl/gui/allwords/13UP_ES-MX_DA-Base_FormatA.xml`

The XMLs are UTF-16, parse correctly, and each contains 12 `wordlist` elements and 2,785 `parts` elements. The HMI binary itself contains text labels such as *Top Menu*, *Car Information Screen*, *Customize Home Screen*, and *Screen off*, and references `/opt/ftl/gui/MC/`, `/opt/ftl/gui/font/`, `/opt/ftl/gui/allwords/`, `allwords_na.xml` and `ScreenTrans.mui`. The recovered file paths and executable path strings are not identical; do not invent a renaming rule or conclude all assets exist.

## DENSO TEN newer source materials

The independently recovered `DENSO_TEN_17_OSS_SOFT_PACK.zip` is newer related-platform source (kernel 3.10.101-ltsi), not identified as original CA01 proprietary source. Evo middleware offers architectural examples, but no functionally/ABI verified replacement for CA01 GUI libraries. `libmmap_hw.so` is **not** an established missing CA01 dependency. No unrelated-source modules were substituted.

## Limitations / next testable milestones

1. In a **new disposable sandbox only**, implement a **minimal, tested display-manager memory/plane interface** based on the recovered `sysDisMng*` call arguments (three `width*height*4` buffers). Do not touch original ELF bytes or source repositories.
2. Test a Mesa ARMEL native-window/EGL **bridge** with a synthetic window shaped like the decompiled structure. A pbuffer fallback is plausible for a first experimental screenshot, but must be validated without misrepresenting it as a factory runtime.
3. Reproduce only the required subset of `fs_cnf_Load`, `fs_ipc_Init`, process callbacks and queue `0x28` based on static evidence. The recovered `libipas_sysc.so` is the source of truth; do not create a hollow dummy `SysPowerOn`.
4. Continue recovering proprietary `libdisplay_if.so`, `libdismng_if.so`, `libipas_std.so` and remaining library interfaces from authentic firmware images. The main GUI has not been executed or rendered.
5. Confirm actual startup task pointers/config tables and EGL extension requirements in subsequent Ghidra passes before implementing interface shims.

Ghidra log notes `Invalid GIF/PNG data` while auto-detecting data at some addresses; these are not proof files are broken. Ghidra also reports 261 unresolved **external project symbols** because other shared libraries were not imported into its project; that is **not** the count of missing shared libraries or files.
